# Baseline diagnosis — 2026-10-24

Recorded at the start of the reliability rework, from `main` at `020d2d2` and production KV. No Onshape API request was made to produce this report.

## Checks on `main`

`pnpm install --frozen-lockfile`, `lint`, `typecheck`, `test` (89 tests), `build`, and the Playwright smoke tests pass. The repository had no CI workflow. The root `build` script calls `pnpm` recursively, so pnpm must be on `PATH`; `corepack pnpm` alone is not enough for that step.

Read with `wrangler kv key get --remote`, at about 12:50 UTC. Only snapshot, pointer, and a cursor size/position summary were read.

Root causes, each verified against a live vendor page or the code:

1. **goBILDA and ServoCity are permanently stuck.** One page without Product JSON-LD throws, the cursor keeps its position, and every later run fails on the same page.
   - goBILDA `2801-series-zinc-plated-steel-washer-4mm-id-x-8mm-od` is a BigCommerce variant-family page. It has only `BreadcrumbList` JSON-LD. Its variant rows carry the SKUs and pack sizes: "25 Pack · 2801-0004-0008 · $1.99" and "250 Pack · 2801-0004-0008-250pk · $9.99".
   - ServoCity `16awg-premium-silicone-jacket-wire-black-3m-length` returns a 2 KB "This page has moved" JavaScript redirect stub to a `?sku=` URL. The sitemap still lists it.
2. **Nothing becomes searchable until a full crawl ends.** The pointer is written only after every page, record, and index write completes. At 40 pages per run and four runs a day per vendor, REV (390 pages) needs about 3 days; ServoCity (5,152) needs about 32 days, assuming no failures.
3. **The cursor holds every collected record in one JSON value.** It already reaches 376 KB at 9 records because it also stores the full URL list. It grows with the catalog.
4. **An absent catalog looked healthy.** `enrichScan` checked freshness only for vendors that matched a line. With no published catalog, nothing matched, so the stale flag stayed false and the Vendor column was simply empty. This explains the HORS scan's "no useful supplier matches".
5. **Workers KV free-plan writes (1,000/day) are a hard budget.** The current design writes one key per record and per name token, which would take days of quota for ServoCity alone. *Not yet verified:* the account's Workers plan. The check that would read it was blocked because it needed the wrangler OAuth token; confirm in the Cloudflare dashboard.

## Onshape scan cost and "missing metadata"

From `apps/worker/src/scan.ts` on `main`:

- One `getAssemblyDefinition` call, then one Part Studio **mass properties** call for every unique source/configuration pair, six at a time. For HORS (193 unique lines plus suppressed lines), that is roughly 150–200 requests per scan, or 6–8% of a 2,500-request annual allowance.
- Every line whose mass body is absent, or whose request failed for any reason, received a missing-metadata reason. Mass is not used for vendor matching. So the reported 194 "missing metadata" entries described mass-property availability, not missing SKUs or part numbers.
- *Hypothesis, not verified:* if the Worker runs on the free plan's 50-subrequest limit, most of the ~190 mass calls would throw after the first ~50. That produces a "Part metadata could not be read" flag on most lines and matches the observed total. The new ledger records thrown requests as `errors.subrequest-limit`, which will confirm or rule this out on the next live scan.
- The 16 requests seen on the Onshape Developer counter were read during a scan, not after it.

## Other findings

- `/api/onshape/*` forwarded any authenticated GET to Onshape. The web app never used it, and it let any session spend the annual allowance. It is removed.
- `rootAssembly.name` is read for the assembly title, but the assembly definition response does not appear to include it, so the UI falls back to "Assembly". To be fixed in the inventory PR with the element name.
- `matching.ts` assigns `confirmed` to fuzzy name scores of 0.72 or higher without a human action, and confirmed lines are priced. This breaks the "fuzzy is a candidate" rule. To be fixed in the matching PR.
- STL fallback uses `POST …/translations`, which likely requires write scope; the app is granted read scopes. The owner chose STEP export instead of STL, so the export PR will verify STEP endpoints and their scopes.
