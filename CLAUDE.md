# Control Kit engineering notes

## Architecture

`Onshape iframe → React/Vite Pages app → Cloudflare Worker → Onshape API`; Worker KV stores encrypted sessions and catalog snapshots. `packages/shared` holds domain logic and `packages/excel` builds exports. The browser never receives OAuth secrets or tokens.

## Repository

`apps/web` is the iframe UI. `apps/worker` owns OAuth, scan/export calls to Onshape, the request ledger, and scheduled ingestion. `packages/shared` owns matching, classification, aggregation, and the Control Point contract. `packages/excel` owns XLSX/CSV export. `fixtures`, `scripts`, and `samples` hold test inputs and generated examples. See README for setup and checks.

The browser calls only the Worker for Onshape data. The Worker keeps access/refresh tokens encrypted in KV; its cross-site iframe cookie is opaque, `HttpOnly`, `Secure`, and `SameSite=None`. Vendor reads use a short Worker memory cache then KV, returning unmatched on a miss without scraping during a scan. Classification, matching, and purchasing rules are shared between app and Worker. External calls have bounded retries/timeouts; user scans are never edge cached. Control Point has no network implementation in v1.

## Milestones and deviations

M0 is scaffold only. M1 adds OAuth and mock Onshape. Scanning, vendor ingestion, classification, STL, and Excel are subsequent milestones. The repository is `ZOGWORK/control-kit`; no Control Point source is modified. (Historical M1 note: at the time no endpoint or feed was verified live. Live OAuth and one HORS scan have since run; see the reliability rework section.) The mock server is reused directly by tests because this sandbox blocks loopback connections. The Worker stores AES-GCM encrypted Onshape tokens under an opaque cookie ID in APP_STATE KV and uses one-use OAuth state. Real iframe behavior, endpoint paths, and scopes await portal verification. Do not use an API key for this App Store flow.

Current Onshape extension docs specify `{$workspaceOrVersion}` and `{$workspaceOrVersionId}` for the Element right panel and label `{$workspaceId}` deprecated. This differs from the brief's iframe parameter assumption, so M1 preserves the current context pair through OAuth. The current Cloudflare CLI delegates a plain `pages project create` command to Workers; `--force` created the explicitly requested Pages project. Subsequent Pages deployments do not use `--force`. Production URLs are `https://control-kit.pages.dev` and `https://control-kit.control-kit-worker.workers.dev`. Cross-site cookie behavior inside a real Onshape iframe remains unverified.

Onshape's sample integrated app sets an OAuth URL separate from the iframe action URL; its Applications-page flow can arrive without Assembly context. The Worker therefore supports context-free `/oauth/start`, validates Onshape's optional `redirectOnshapeUri` against `https://cad.onshape.com`, and returns to that page after OAuth. This replaces the earlier README instruction to leave the OAuth URL blank. The source is [Onshape's sample app](https://github.com/onshape-public/app-gltf-viewer) and [Onshape help](https://onshape-public.github.io/docs/help/). The Onshape OAuth guide explicitly says third-party cookies must be enabled for embedded apps; real-browser behavior still needs validation.

M2 pins `ONSHAPE_API_VERSION=v9` from the official [assembly](https://onshape-public.github.io/docs/api-adv/assemblies/) and [Part Studio](https://onshape-public.github.io/docs/api-adv/partstudios/) examples. The API Explorer and a real response still need validation with the owner's OAuth app; no Onshape API requests have been made. M2 fixtures are synthetic but use the documented `rootAssembly.instances` and `subAssemblies.instances` fields. We added `missingMetadataReason` and `unresolvedSubassembly` to `BomLine` because the brief requires a reason and a fallback line but its interface omitted fields for them. The missing-metadata view includes suppressed lines with failures; suppressed quantities remain excluded from active totals. Mass properties are fetched once per unique element, with six concurrent requests, while assembly definition is fetched once. Later vendor matching/classification will extend the M2 types.

Greptile identified a real source-revision issue in M2. `bomLineKey` now appends source type/ID to the brief's document/element/part/configuration key so different revisions cannot merge. Subassembly lookup and recursion ancestry include document microversion. `BomLine` also carries `sourceType` and `sourceId`; linked parts without a source revision are marked as missing metadata rather than fetched from the root assembly's workspace. Mass-property calls group by source and configuration and pass the configuration query value. An explicitly empty subassembly contributes zero parts. A failed OAuth refresh emits a reconnect event, including during metadata calls.

M3 adds `partNumber`, `matchStatus`, `matchReasons`, `packsToOrder`, and `lineTotalUsd` to `BomLine` and `packSize`/`packSizeVerified` to `VendorRecord`. `priceUsd` means the charged price for one purchasable pack. A line total is blank unless both the match and pack size are verified; possible matches never contribute to purchasing totals. An exact normalized SKU sets Commercial before the print classifier, with manual override reserved for M5. Per-user/document/line confirmations are stored independently at `match-decision:{userId}:{documentId}:{sha256LineKey}` in APP_STATE, with vendor ID and normalized SKU so a changed catalog match cannot inherit an old decision. A fixed-length hash keeps configured-part keys within KV limits. This added key differs from the brief. Vendor fixture data lives in `fixtures/vendors/seed.json`, is only loaded with the explicit local-only seed command, and is never the production catalog. The read path uses a 60-second in-isolate cache, KV keys from §6, and at most 20 concurrent KV gets.

M4 source checks (2026-10-23): [REV](https://www.revrobotics.com/xmlsitemap.php), [ServoCity](https://www.servocity.com/xmlsitemap.php), and [goBILDA](https://www.gobilda.com/xmlsitemap.php) serve BigCommerce product sitemaps and Product JSON-LD on product pages. [AndyMark](https://andymark.com/sitemap.xml) and [Pitsco](https://www.pitsco.com/sitemap.xml) serve Shopify product sitemaps and Product JSON-LD. REV, ServoCity, and goBILDA `/products.json?limit=1` returned 404; AndyMark and Pitsco returned 429 to that feed probe. The brief's assumption that REV and ServoCity have usable Shopify feeds is incorrect. All five pipelines therefore start from the public product sitemap; no scrape-only pipeline is needed. `fixtures/vendors/captured/` holds compact extracts of the observed sitemap links and product JSON-LD, not a production catalog. Product sitemaps on Shopify also include the store homepage, which the pipeline filters out. Read-only live samples using an isolated in-memory KV fetched/upserted goBILDA 1/1, ServoCity 1/1, AndyMark 4/4, REV 1/1, and Pitsco 2/2; production KV was not touched, and zero Onshape requests were made.

M4 KV deviation (superseded by PR 2 below): `vendor:{vendorId}:__cursor__` stores resumable crawl/publish progress, and a SHA-256 content version identifies `vendor-version:{vendorId}:{version}:{normalizedSku}` plus `vendor-index-version:{vendorId}:{version}:{token}`. The `__lastgood__` pointer changes only after every record and index in a new version is written and 65 seconds have passed for [cross-location KV propagation](https://developers.cloudflare.com/kv/api/write-key-value-pairs/); scans continue reading the old version during partial runs or failures. `__snapshot__` is a separate status write on **every** successful or failed run. Its `inProgress` field marks a successful partial batch, and `updatedAt` is the last complete refresh, used for staleness because unchanged products do not need rewriting on each identical crawl. `ScanResult.vendorDataUpdatedAt` is added for the UI timestamp. A detected pack size comes only from explicit product text such as “Pack of 10”; otherwise purchasing totals remain blank.
M4 review hardening: failed sitemap fetches and product pages without usable Product JSON-LD retain their cursor position and fail the run, preserving the last-good catalog. A snapshot's successful refresh time applies only when its version equals the pointer selected by the scan. Version manifests and `vendor:{vendorId}:__retired__` queue replaced catalogs for incremental deletion after a 24-hour reader grace period; cleanup never deletes the active pointer's version or a version being rebuilt and is limited to 40 keys per run. If catalog content returns to a retired hash, the retirement is cancelled before its versioned writes resume.
M5 data additions: `settings:{userId}` holds `{teamNumber}`; `override:{userId}:{documentId}:{SHA256(partIdentity)}` stores each manual type independently, where `partIdentity` is `documentId:elementId:partId:configuration` and does not include the source revision. Each line adds `manualClassification`. A completed scan gets a UUID `scanId` and is cached at `scan:{userId}:{scanId}` for one hour so an authenticated STL export uses the exact assembly tab/revision the user scanned. The ZIP route re-reads settings, match decisions, and per-line overrides before selecting printed lines. These KV shapes and the one-hour scan cache were needed to implement persistent overrides and a bounded export source. Official [Onshape export docs](https://onshape-public.github.io/docs/api-adv/translation/) show async results in `resultExternalDataIds[]` and synchronous STL's 307 redirect; the Worker uses that array and follows same-origin authenticated redirects. STL requests include the scanned configuration. The STL paths are exercised against the mock Onshape server only; real v9 response and permission validation remains a live gate and has spent zero Onshape API requests.

M6 workbook deviation: the user's settled purchasing rule adds separate `Qty Needed` and `Packs to Order` columns, so the BOM has 13 columns instead of the brief's 12. Pack Price is the charged price per purchasable pack. A line gets the formula `=Drow*Grow` only for a confirmed/exact match with a verified pack size and known price; unknown pack size or a possible match leaves Line Total blank. Row 4 uses separate label/value cells and an unmerged live Estimated Total formula at F4. `BomLine.alternatives` stores up to three ranked same-vendor/category in-stock catalog records for low/out-of-stock lines. `printCategory(name)` is shared by the STL zip and Excel sheet to keep folders consistent. The four-sheet XLSX is built by a pure browser-compatible function and uses the scanned result without new Onshape requests.

M6 review hardening: the workbook's vendor date uses `ScanResult.vendorDataUpdatedAt` (last completed refresh) before falling back to the oldest used record timestamp, because unchanged products retain their older `VendorRecord.updatedAt`. The BOM keeps the brief's first-alternative link in the line's Alternatives cell and lists each alternative again in a detail block with its own SKU and product hyperlink. The AutoFilter ends at the last commercial line so merged printed and alternative headings cannot prevent Excel sorting; those later sections remain visible below the filter.

M7 scope follows the user's correction over §14 and §18: Control Point is only an interface and in-memory test adapter. There is no HTTP adapter, link/sync UI, or live network path until its real BOM endpoint and auth are confirmed. `buildControlPointPayload` creates a stable SHA-256 idempotency key from document, element, source revisions, and BOM content rather than the random scan UUID. The test adapter records payloads and reuses a mock ID on repeat; unlink is test-only. The browser smoke routes session/scan calls to local fixture responses while existing integration tests exercise the mock Onshape server directly. Excel failure reveals a CSV fallback built from the same BOM sheet model. Generated XLSX and mock STL samples live in `samples/`.

The Control Point payload changes the brief's ambiguous `unitPriceUsd` to `packPriceUsd` and adds `packsToOrder`, `lineTotalUsd`, and `matchStatus`. CAD `qty` stays individual units; a receiving system must never infer an order total from `qty × packPriceUsd`. `lineTotalUsd` remains null until pack size and match are verified. This interface will be mapped to Control Point's real schema only after that API is confirmed.

M7 review hardening: CSV text fields escape formula-leading content from Onshape part names, while quantities and cached totals remain numeric. The Control Point idempotency hash includes assembly name, suppressed count, totals, canonical line data, and source revisions; only `generatedAt` is excluded so a repeated unchanged scan reuses the same key.

Brand update: Control Point's published theme uses near-black `#09090b` and yellow `#ffc700`; Control Scout describes its UI as sharing that design language. Control Kit now uses those colors in the iframe and workbook. Its distinct transparent hexagon-and-circuit-K logo lives at `apps/web/public/control-kit-logo.png` and is embedded in the BOM sheet as a PNG drawing. The browser loads that local static asset when producing an XLSX, and the sample generator supplies the same bytes. A workbook built without a logo remains supported for pure callers and CSV export. The BOM header now merges `A1:B3` for the mark and starts its title/metadata at `C1`; row 4 and all purchasing formulas are unchanged. All four sheets use the same black/yellow headers; stock green/red/gray remains semantic. ## Reliability rework (from 2026-10-24)

The rework follows the owner's brief in seven dependency-ordered PRs: baseline, catalog, inventory, manufacturing model, export, UI/Excel, launch check. The catalog PR moved ahead of inventory because it does not depend on Onshape and its crawl needs wall-clock time. [docs/baseline-2026-10-24.md](docs/baseline-2026-10-24.md) records the starting state and verified root causes: no vendor has ever published a catalog, two crawls are permanently stuck, the scan makes about one mass-properties call per unique part, and "missing metadata" meant mass unavailable.

PR 1 (baseline and diagnostics):
- `apps/worker/src/onshape-client.ts` counts every outbound Onshape request by endpoint kind, status, and retry. All Onshape calls (OAuth profile, scan, export) go through `countedFetch`. Thrown fetches are counted by error name only, so messages carrying URLs or IDs never reach KV.
- One aggregate per operation folds into `APP_STATE` `onshape-ledger:YYYY-MM-DD` (400-day TTL). The aggregate is read-modify-write, so simultaneous operations can under-count; the Onshape Developer counter stays authoritative. Live development requests are logged by hand in [docs/onshape-request-ledger.md](docs/onshape-request-ledger.md).
- `BomLine.metadataIssue` adds a stable `{ code, httpStatus }`. `missingMetadataReason` keeps the user text from `metadataIssueText`. `ScanResult.diagnostics` holds the scan's request summary and issues grouped by code, status, and source type.
- `catalogHealth()` reads only the snapshot and pointer for each of the five vendors. It returns `published`, `building`, `failing`, or `never-run`, with staleness, last error, and crawl progress. The snapshot now carries `progress` so health never reads the large cursor. Health is attached to every scan (`ScanResult.catalogHealth`), shown as a warning even when no line matched, and served publicly at `GET /api/catalog/health`.
- The unused `/api/onshape/*` passthrough is removed: any session could spend the annual allowance through it.
- CI (`.github/workflows/ci.yml`) runs install, lint, typecheck, unit tests, build, and smoke with no secrets. `node --experimental-strip-types scripts/ops-report.ts` prints catalog health and the request ledger from production KV, read-only.

PR 2 (vendor catalog and matching):
- **Storage.** `vendor-ingest.ts` replaces the per-record, per-token, and cursor-with-records layout with the `cat:{vendor}:…` layout described at the top of that file:
  - **pointer** — the live generation;
  - **crawl** — position only;
  - **urls** — one list per sitemap;
  - **append-only batches**;
  - **[sku, name, batch] index**.

  A run costs about five KV writes. `vendor:{vendor}:__snapshot__` stays the per-run status record and now carries `complete`, `progress`, and `skipped`. The first run of the new pipeline deletes the legacy `__cursor__`/`__lastgood__`/`__retired__` keys. M4's versioned keys were never written in production because no crawl reached the records phase.
- **Publication barrier.** A run first publishes what earlier runs wrote, then fetches. `pointer.batches` tells readers which batches they may use, and readers ignore index entries for later batches. When a later page re-lists a SKU, its index entry keeps the previous batch as a fourth field, so the product stays readable until the newer batch is published. KV takes up to about 60 seconds to propagate, so nothing becomes visible until the next cron run, an hour later.
- **Publication.** The first crawl goes live in parts, one run behind, labeled partial. Refresh crawls build a separate generation and switch only on the run after completion. `pointer.previous` keeps the replaced generation for 24 hours, then deletes it at up to 20 keys per run. Retirement never deletes `pointer.gen`. Manual rollback means setting `pointer.gen` to `previous.gen` and `previous` to null.
- **Failure handling.** A run that fails mid-crawl writes the records it already fetched before saving its advanced position. A crawl that ends with no usable records, for example behind a challenge page, is discarded and restarts next run; the published catalog stays live. Completed catalogs keep their skipped-page counts in `pointer.skipped` and the snapshot.
- **Parsing order.** Shopify `var meta` variants first, then BigCommerce `card-body child` rows, then Product JSON-LD.
  - Records without a real SKU are rejected; the old parser derived a SKU from the product name.
  - `VendorRecord` gains `packEvidence`, `parser`, `sourceUrl`, and `catalogVersion`. Pack size counts only with explicit wording (`packFromText`). Shopify variants use the variant label first, then the product title.
  - Skip reasons are `redirect-stub`, `no-product-data`, `no-sku`, `robots-disallowed`, `off-vendor-url`, and `fetch-failed`. A failing fetch holds position for three runs, then is skipped.
  - Fixtures in `fixtures/vendors/pages/` are trimmed copies of real pages from 2026-10-24, including the two pages that froze goBILDA and ServoCity.
- **Reader.** `catalog.ts` reads each pointer and index once (60-second isolate cache). It ranks name candidates with the matcher's own score (`nameSimilarity`, including the size/number penalty), so the 12-candidate cut cannot drop the record the matcher would choose. It reads only the batches holding candidates. Freshness comes from each matched record's fetch time, and `VENDOR_STALE_HOURS` is now 336 to cover a full refresh cycle. Crons run every hour per vendor (PR 6c; every two hours before that, every six originally).
- **Matching** (brief rule 3):
  - `classifyMatchScore` never returns `confirmed`; only a `MatchDecision` from a person does, so fuzzy name matches are never priced automatically. The fixture tests' screw and wheel lines, previously priced from name similarity, are now `possible` with blank totals.
  - An exact SKU at several vendors stays `exact` when the product names agree and every size or number token matches; ServoCity sells goBILDA items under goBILDA SKUs, as the live sample showed. Otherwise it becomes `possible`; M3 and M4 versions of a screw are not the same product.
  - `skuCandidates` also accepts dashed all-digit tokens of 8+ digits (goBILDA `5203-2402-0019`). It still rejects bare numbers in names; numeric-only SKUs such as Pitsco `44260` are trusted only from the part number.
  - Exact-match reasons say whether the SKU came from the part number or the name.

PR 3 (Onshape inventory through the BOM):
- **Requests.** A scan reads the workspace's current microversion, then the assembly definition and the flattened BOM (`indented=false`, all columns, `generateIfAbsent=true`) *at that microversion*, so both describe the same immutable revision. That is 3 requests, plus 429 retries; the old flow made one mass-properties request per unique part (about 190 for HORS). A version context skips the microversion request. Mass properties are no longer fetched: nothing used them, and their absence was what "missing metadata" used to mean.
- **Cache.** The definition and BOM are cached in APP_STATE at `{userId}:onshape-source:{documentId}:{elementId}:{m|v}:{id}` for 30 days, but only when both reads succeeded. The cache is per user, so it never serves data to someone whose own Onshape access has not read it. A rescan of an unchanged workspace costs 1 request.
- **Merge.** `packages/shared/src/bom.ts` maps BOM columns by `propertyName`, then display name (`partNumber`, `description`, `vendor`, `material`, `quantity`, `name`). Cell values may be strings, numbers, or objects (`displayName`/`value`). Rows match lines by document/element/part/configuration, with `default` treated as no configuration and a single-row fallback per part.
  - The BOM name, part number, description, and material fill the line; `BomLine.bomProperties` keeps the raw fields.
  - The row's `wvmType`/`wvmId` fill a missing source, fixing linked-part links.
  - The assembly name comes from `bomSource.element.name`, and `ScanResult.documentName` from `bomSource.document.name`.
- **Reason codes.** `unresolved-subassembly`, `unresolved-reference` (instance `errorStatus` or a non-OK `status`), `source-revision-unavailable`, `not-in-bom` (active lines only, since Onshape omits suppressed instances by design), and `bom-unavailable` (with HTTP status; the scan still completes from the definition).
- **Diagnostics.** `diagnostics.bom` reports rows, matched lines, lines without a row, rows without a line, and quantity mismatches, plus each column's id, `propertyName`, and sample value type, without any part data. A live scan therefore shows whether the mapping above fits real BOMs. `diagnostics.revision` and `diagnostics.cache` record what was read.
- **Allowance.** Onshape counts only 2xx/3xx responses against the 2,500-request allowance, so the ledger now reports `billable` separately from `total`. A 402 ends the scan with an explicit annual-allowance message.

PR 4 (manufacturing model):
- **Fields.** `classifier.ts` replaces the keyword score with `decideDisposition`. Each line carries:
  - `disposition`: `buy`, `print`, `cnc`, `cut-2d`, `fabricate`, or `review`;
  - `dispositionSource`: `manual`, `exact-sku`, `explicit-metadata`, `provenance`, `suggestion`, or `none`;
  - `dispositionConfidence` and `dispositionEvidence`;
  - `reviewReason` and `suggestedDisposition`;
  - `provenance`: `vendor-catalog`, `standard-content`, `linked-library`, `team-design`, or `unknown`.
- **Precedence.** Manual, then exact SKU (Buy), then explicit metadata (BOM `process` column, complete bracketed or `#` team tags, print materials, all matched as whole words; values naming two processes go to review), then provenance (standard content, a linked library part with a part number, a confirmed match), then suggestion, then none. Suggestions and no-evidence cases are always `review`; heuristics never decide alone. A manual override on an exact-SKU part keeps the SKU and adds an "exception" evidence line.
- **Legacy view.** `classification` (`commercial`/`printed`/`unknown`) is still derived from the disposition for the export code that reads it, until the UI/Excel rework. `classificationScore` is always 0 now. The print export selects only `disposition === 'print'`, so name-only print suggestions are no longer exported until confirmed.
- **Shared overrides.** The current choice is stored per document at `disposition:{documentId}:{sha256(identity)}` as `{ disposition, by, byId, at }`, last write wins. KV has no atomic read-modify-write, so every change is also written to its own never-overwritten key, `disposition-change:{documentId}:{hash}:{at}:{uuid}`, kept for a year; concurrent saves therefore never erase history. Clearing a choice stores `disposition: null`.
  - A write needs the writer's own `scan:{userId}:{scanId}` for the same document, which proves Onshape access.
  - The pre-rework per-user `override:{userId}:{documentId}:{hash}` keys (`commercial`/`printed`) are read as a fallback via `parseOverride` and deleted when the part is set again.
  - The BOM merge now also maps a `process` column (`process`, `manufacturing`, `makebuy`, …).

PR 5 (STEP export, replacing STL at the owner's request):
- **Removed.** `stl-zip.ts`, its route `/api/prints/zip`, and the STL sample.
- **Job flow.** `step-export.ts` turns the export into a job:
  - `POST /api/exports {documentId, scanId}` reapplies current match decisions and dispositions to the cached scan. It then creates `export:{userId}:{jobId}` (1-hour TTL) with every active part whose disposition is print, cnc, cut-2d, or fabricate (`wantsStep`).
  - `GET /api/exports/{jobId}` advances the job within 30 Onshape requests: start pending translations, poll running ones, then download, check (`checkStep`), and store finished files at `export-file:{userId}:{jobId}:{index}`.
  - `GET /api/exports/{jobId}/files/{index}` serves a stored file without another Onshape request.
- **Export source.** `createPartStudioTranslation` accepts only a workspace or version, not a microversion. Each line therefore carries `exportSource`: the assembly's own workspace or version for parts in its document, the instance's `documentVersion` for linked parts, or the BOM row's `wvmType`/`wvmId` when it is `w` or `v`. A part without one fails with a reason.
- **ZIP.** `packages/excel/src/step-zip.ts` builds it in the browser with `MANIFEST.txt` (`exportManifest` in `packages/shared/src/step.ts`), and throws `NoStepFilesError` when nothing succeeded. The shared Worker helper `onshapeFetcher` handles token refresh and 429 retries for export calls.
- **Not yet validated live.** Real STEP output, its `resultDocumentId` and externaldata download, and import into a slicer/CAD viewer.

PR 6 (UI redesign, at the owner's request to match Control Scout and Control Point):
- **Library.** Arc components (uiarc.dev) are vendored into `apps/web/src/components/arc` with the shadcn CLI (`apps/web/components.json`; `apps/web/tsconfig.json` exists only so the CLI resolves `@/`). They are excluded from lint as third-party code; the one local patch is a null guard in `drawer.tsx`. Arc needs React 19, so the web app moved from 18 to 19.
- **Theme.** `styles/theme.css` imports Arc's `foundation.css` and maps its tokens onto the Control palette (the same values as Control Scout's `index.css` and `arc-theme.css`). Fonts are Control Scout's self-hosted variable Inter, Space Grotesk, and JetBrains Mono (OFL). Arc's primary button is neutral by design, so `Button` in `app/bits.tsx` re-points `--foreground`/`--background` on primary buttons to get the volt primary without editing Arc. The owner asked for no showy animation, so there is no ambient grid or motion beyond Arc's own transitions.
- **Structure.** `app/useControlKit.ts` holds all state and server calls (unchanged behaviour from the old `main.tsx`, plus sign-out and `acceptSuggestions`). `app/model.ts` holds the pure view logic (summary, review queue order, buy list grouping, part filters), tested in `model.test.ts`. Each section is one file. `.tab` rows replace the sidebar under 900 px. Excel, CSV, and ZIP builders load on first download (dynamic import).
- **Classifier.** The live HORS queue showed many purchased parts with vendor part numbers or hardware names (goBILDA `2106-4008-0560`, "1501 Series", McMaster `91290A110`, "M4 x 0.7mm Locknut", "E-Clip", "HTD5 Belt") sitting undecided or suggested as prints. They now *suggest* Buy (never decide), with print wording still taking precedence. On the saved HORS scan, undecided parts drop from 145 to 60.
- **Fixture mode.** `vite --mode fixture` (`pnpm --filter @control-kit/web fixture`) adds `fixture-api.ts`, a stand-in for the Worker API serving the robot fixture or the scan named by `CK_FIXTURE` in an untracked `.env.fixture.local`; `*.local` is git-ignored.

PR 6b (workbook redesign): six sheets in the app's order (Overview, Buy list, Make, Review, Links, Exceptions), replacing the four-sheet BOM. The owner asked for a Links sheet linking every part to its product and its Onshape part. The money rules are unchanged: `Line Total = E×H` only for exact or confirmed matches with a verified pack and price, and the subtotal reads "None priced" rather than $0.00 when nothing is priced. Make reproduces the STEP export's file names by running `stepFileName` over `lines.filter(wantsStep)` in the same order. Checked by opening the HORS and a synthetic 12-screw workbook in Excel (no repair prompt, formulas recalculate to $17.98, links counted per sheet) and rendering each sheet.

PR 6c (catalog throughput, after production showed AndyMark and Pitsco failing with HTTP 429 and no vendor published after a day):
- **Shopify feed.** `vendorSources[v].feed` marks AndyMark and Pitsco. Their crawl reads `/products.json?limit=250&page=N` (`parseShopifyFeed`), up to `maxFeedPages` (4) pages per run, and ends at the first empty page. Crawl state reuses `Crawl`: `urlIndex` is pages read and `sitemapIndex` becomes 1 at the end. Batches, index, and publication are unchanged. A probe from Cloudflare's edge got HTTP 200 for robots, sitemap, and the feed at a gentle pace, so the 429s came from the page-by-page crawl rate, not an IP block.
- **429 retry.** `fetchText` retries a 429 twice after `Retry-After` (capped at 10 s, default 2 s) before failing the run. Every attempt counts against `maxRequests` (47, under the 50-subrequest limit); loops stop starting fetches at the limit, and a retry the run cannot afford ends it through the normal failure path, which saves progress.
- **Feed safety.** A feed body without a `products` array throws; only an explicit empty list ends a crawl. A Shopify vendor's crawl saved in the old sitemap format is dropped and restarted as a feed generation (its unpublished keys are left behind; production had none, since both vendors failed before a crawl was saved).
- **Refresh pacing.** No new crawl starts while `pointer.previous` awaits deletion, so feed vendors (which finish in two runs) refresh about once a day and every replaced generation is retired.
- **Hourly crons.** `cronVendors` in `apps/worker/src/index.ts` maps each `wrangler.toml` cron to a vendor; a test fails if a scheduled cron has no vendor. KV writes stay near 600 a day at about five per run.
- **Paused (2026-10-25).** After Cloudflare warned that the account had used 50% of the daily KV limit, the owner asked to stop refreshing vendor sites. `crons = []`; the schedule is kept as a comment in `wrangler.toml`. Published catalogs stay live and read normally; after `VENDOR_STALE_HOURS` (14 days) they show as stale. Official feeds the owner has asked vendors for would load through `scripts/catalog-load.ts` without crons.

- **AI review scope.** `packages/shared/src/ai-review.ts` selects only the ambiguous bucket (`needsAiReview`): possible matches, no match with near matches, undecided or low-confidence dispositions, and Buy lines with an unknown pack. Audit 1 (security, from the full audit of 2026-10-25):
- **OAuth state.** `/oauth/start` no longer writes `oauth-state:*` to KV (anyone could spend the 1,000 daily free-plan writes by opening it). The state rides in a signed, HttpOnly `controlkit_oauth` cookie (HMAC-SHA-256, key derived from `SESSION_ENCRYPTION_KEY`, `Path=/oauth`, 10 minutes), so a redirect also completes only in the browser that started sign-in (no login CSRF). A one-use `oauth-used:{state}` key is written only after Onshape accepts the code, so made-up callbacks write nothing.
- **Session.** Only `{id, name}` from `sessioninfo` is kept. `/api/session` re-saves a session at most once a day (`savedAt`). `/api/logout` checks Origin.
- **AI route.** `trustedAiRequest` rebuilds every line from the caller's own stored scan (name, description, material, part number, configuration, places used, quantity, source, review reason). Only the browser's catalog candidates (each id must equal its vendor plus normalized SKU, names cut to 160 plain characters) and its enum-checked conclusion are kept; unknown fields are dropped. Body cap 150 KB. Cached answers write nothing. The cache key includes both configured models. A blank key counts as no key, for enabling and for choosing the provider.
- **AI allowance.** A Durable Object, `AiAllowance` (`apps/worker/src/ai-allowance.ts`, binding `AI_ALLOWANCE`, SQLite-backed so it runs on the free plan), holds the per-person 20/day, the global 300/day, and the 200-second per-person lock. It reserves atomically, so concurrent reviews cannot exceed either limit. It decides the UTC day itself, drops older days' counts on a new day, and keeps running-review locks across midnight. AI lines join the scan by `bomLineKey` (sent beside the request, never to the model), not by name. The review is off without the binding.
- **Shared part types.** An override must name a part that is in the writer's scan.
- **Export polls** write the job only when it changed; with every running translation checked, the polling position wraps back and nothing is written. A 5-minute export polled every 2 s used to cost about 150 writes.
- **Framing.** `apps/web/public/_headers` sets `frame-ancestors 'self' https://cad.onshape.com https://*.onshape.com`. `postMessage` targets `https://cad.onshape.com`. `.gitignore` covers `.env.*`.
- **Not changed, owner decision:** anyone who can read a public document can scan it and change its shared part types (history keeps who). Limiting writes to editors needs an Onshape permission read per write.

Audit 2 (quantities and matching, from the full audit of 2026-10-25):
- **Pieces of one product.** `recalculatePurchasing` (`studioQuantity`) counts bodies of one Part Studio sharing a SKU by where the Part Studio comes from. Linked from another document, they are a vendor's model of one product in pieces (REV's switch), so in each assembly the product count is the most of any piece there, and assemblies add up. In the team's own document they are the team's parts (screws modelled in place) and add up. Copies of one piece ("Screw 1", "Screw 2") always add up. Before, every Part Studio took its largest count, so four in-place screw bodies placed 30 times each ordered 30 screws instead of 120.
- **Kit folding** compares the configuration (`doc:element:configuration`) and never folds standard content; eight screws beside an imported motor used to vanish into it.
- **Linked subsystems.** `groupingWords` adds subsystem words (arm, linkage, box, block, claw, intake, outtake, turret, drive, lift, slide, …), and a plural product word ("Intake Wheels", "Drive Motors") means a grouping, so these expand into their parts instead of being listed as one bought product.
- **Bare-number part numbers** match only vendors whose SKUs carry no letters (`skuMatches`): a team part numbered 1001 no longer exact-matches AndyMark am-1001, while Pitsco 44260 and goBILDA's dashed numbers still match.
- **Fastener false positives.** Made parts with fastener words (Captive Nut Plate, Lead Screw, Screw Jack, Snap Ring Groove Shaft) are not stock fasteners.
- **Match decisions** are saved under the part (`decisionIdentity`: document, element, part, configuration), not the line key, whose last field is the workspace microversion and changed on every edit. Reads fall back to the old revision-keyed decision. A pick that is none of the line's records confirms nothing.

## Tuning, tests, and release

Match normalization, thresholds, and alternative ranking are in `packages/shared/src/matching.ts`; an exact SKU still forces Buy absent a manual override. Disposition rules (`decideDisposition`), word lists, and print folders are in `packages/shared/src/classifier.ts`; order quantities are in `packages/shared/src/purchasing.ts`. Vendor stale hours and cron schedule are in `wrangler.toml`; catalog crawl batch limits are in `apps/worker/src/vendor-ingest.ts`. Scan request flow, source cache, and backoff are in `apps/worker/src/scan.ts`; BOM column mapping is in `packages/shared/src/bom.ts`; STEP export job bounds (per-call request budget, 5-minute translation timeout, 20 MB file cap) are in `apps/worker/src/step-export.ts`. Change these with fixture tests and record any changed data shape here.

Run `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm exec playwright install chromium`, `pnpm test:smoke`, and `pnpm build`. `pnpm sample:excel` and `pnpm sample:step` regenerate the committed samples. Release only from a reviewed and merged `main`: deploy Worker, build and deploy Pages with README commands, check `/api/session`, then run `node --experimental-strip-types scripts/ops-report.ts` to check vendor health and the request ledger. The root `build` script calls `pnpm` recursively, so pnpm must be on `PATH` (`corepack enable pnpm`). Greptile must score the exact PR head 5/5 with zero unresolved threads before merging.

The §16 failure matrix is covered by mock tests and UI paths: assembly 403/404/network emit fatal scan errors with retry guidance; 429 backs off with progress; expired tokens refresh once or reconnect; metadata failures appear on affected lines; catalog misses leave lines unmatched; failed/stale catalog refreshes keep last-good data and warn; STEP failures appear per part in the app and in MANIFEST.txt, and an export where every part fails produces no ZIP; Excel exceptions expose CSV; missing assembly context shows an explainer; duplicate scans/exports are guarded. Control Point sync failure is deferred with the live integration by the user's v1 scope correction.
